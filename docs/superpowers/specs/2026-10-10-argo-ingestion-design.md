# Local Argo CD notification ingestion

Status: approved by maintainer on 2026-10-10; implemented and verified in the local sandbox.
Date: 2026-10-10
Base: `454931fe83f3e89aeb218f9d446941b4ed30e25d`

## Intended outcome

Connect an explicitly selected Argo application to one Clio workspace/service, preserve authenticated operation evidence durably, and produce immutable results for an owner-selected closed UTC reporting period through the existing pinned OEMS boundary. Verify the notification producer against a real Argo CD controller in a dedicated Docker-backed Kind sandbox. Keep existing GitHub, identity and mock paths working.

The maintainer requested GitOps deployment tracking, configurable sources, Docker-based Argo verification and clear real-source onboarding. Notifications are the approved first transport; polling/backfill is a separate later capability. The maintainer approved this choice and authentication contract before product implementation.

## Transport alternatives

1. **Authenticated notifications, recommended:** matches the existing `clio.argocd.operation.v1` evidence boundary and preserves operations before current Application state is replaced. A dedicated source credential grants ingestion only, not Argo or browser identity access. Notifications can be missed; coverage stays incomplete.
2. **Read-only Argo API polling:** useful for verification/reconciliation, but current state and bounded history cannot reconstruct every status, past health or consumer exposure. Requires additional endpoint/CA/SSRF policy and native-response mapping. Does not solve stable operation identity alone.
3. **Notifications plus polling:** greater scope and operational complexity. Defer until the first durable evidence path is proven.

## Private configuration and service binding

Use a server-only `ARGO_INGESTION_GRANTS_FILE` setting. All configuration absent disables this transport; invalid/partial configuration prevents startup with a redacted error. Files are owner-only regular files outside Git checkouts, with no symlinks, matching GitHub's private-file policy. API and worker load immutable snapshots and restart together after grant changes.

Each operator grant binds a public opaque source UUID to one workspace and service, stable Argo instance identity, Application UID/name/namespace, AppProject, destination cluster identity and namespace, configuration-repository identity and one environment. A separate referenced private token file holds a random 256-bit bearer credential. At most 100 sources; source and application bindings must be unambiguous. Duplicate credential digests across sources are rejected. Neither token contents nor private paths appear in SQL or HTTP. A fingerprint pins the complete grant, including credential digest, to each connection/run; changing a grant fences old work and requires owner re-save.

Only a current workspace owner can enable or disconnect the granted source. Browser mutations retain exact-Origin enforcement and fresh database session/membership checks. Members can read connection metadata and safe results. App creation/recreation changes UID and requires a new grant; payload names alone do not establish identity.

Connections are immutable revisions, separate from mock settings and GitHub connections. Save selects granted source, requires `applicationOperationsBelongToService:true`, sets its production classification from the operator-selected environment, and accepts an optional versioned exposure-policy reference for the Succeeded signal; it does not infer provider access from GitHub login. Disconnect prevents new receipt/processing, fences pending runs and retains historical receipts/results. Initial receipt time remains unknown until the authenticated producer sends evidence. Every receipt pins grant fingerprint and the full scope tuple. Reconnected revisions can use receipts only with the identical fingerprint and scope; drift never mixes old/new applications. Disconnect/reconnect boundaries are persisted as gaps, one per boundary (two per pair); an active policy-only re-save adds none. Source-lifetime counters, budgets and operation metadata survive grant revisions; eligible retained evidence and gaps remain fingerprint-scoped.

## Machine ingress and immutable receipts

Proposed route: `POST /api/argo/sources/:sourceId/operations`. This is a machine endpoint outside browser session authentication. Authenticate headers before parsing the body. Unknown source and bad credential return the same redacted 401. It requires an exact bearer credential, bounded JSON content type/body (64 KiB), and constant-time digest comparison; it accepts no query-string token, browser cookie authorization or payload-selected workspace/service. Credentials and payloads are never logged. Bearer authentication identifies the trusted operator-controlled producer and anyone able to read its Secret or edit its notifications ConfigMap; it is not controller attestation or HMAC. A stolen credential can forge evidence within its scope. Real deployments must use trusted HTTPS at their chosen ingress; local sandbox delivery uses an isolated loopback relay and does not change the public API bind address.

Envelope is `clio.argocd.notification.v1`, a strict bounded subset of native fields: Application UID/name/namespace, project, destination server/name/namespace, single-source repoURL, booleans indicating sources/sourceHydrator, OperationState phase/startedAt/finishedAt/retryCount, original operation info array and initiatedBy, SyncResult revision/revisions, and Application status.health status/lastTransitionTime. Unknown keys are rejected. The template safely JSON-encodes only these native fields; Clio derives operation identity, timestamps, kind, scope and status revisions server-side before invoking `normalizeArgoOperation`. Every scope field must match the selected grant and active immutable connection. Producer-supplied `observedAt`, coverage or result fields are rejected. Private ingress acknowledgement exposes receipt UUID and original trusted receiver timestamp only.

Within a short transaction, recheck active connection and current grant, stamp first observation using the database clock, validate/derive/normalize from unknown, and append receipt plus canonical digest. Original operation metadata (UUID, startedAt, configuration revision/repository and kind) is immutable; reusing the UUID with conflicting metadata returns 409. The digest canonicalizes contract version plus normalized scope/operation/status fields with deterministic object-key ordering, excluding receipt time and private credentials. Receipt identity is `(sourceId, applicationUid, operationId, notificationRevision)`. After current credential/grant/connection authorization, identical retries return the original receipt and first observation before applying new-arrival age/horizon checks. Content digests identify notifications, so semantic conflict detection is at operation-metadata identity, not a claim that a content hash can collide in ordinary use. Invalid credentials/scope are rejected before useful private metadata is returned. Authenticated scope drift increments a bounded per-source counter; foreign payload details are not retained. Disconnect/grant revocation blocks even retries; receipt replay is not a permission bypass.

Authenticated scope-valid events that cannot be normalized append a minimal immutable gap receipt: digest, granted Application UID, native start time when valid, receiver time and bounded reason code (`unmarked_operation`, `non_terminal`, `missing_sync_result`, `missing_health_timestamp`, `multi_source`, `source_hydrator`, `future_timestamp`, `invalid_operation_info`, `observation_horizon`). No evidence or raw body is attached. Duplicate gaps replay without new rows. Result reports recorded gap count and reason totals; zero recorded gaps never proves delivery completeness.

Apply a per-source in-memory limit of 30 requests/minute with burst 10 before opening a database transaction; excess returns retryable redacted 503. Each operation accepts at most 30 distinct (phase,health) combinations, with subsequent changes within an already accepted combination treated as an unsupported gap, not new evidence. Bound retained receipts/evidence per source/service to 5000 total rows and 8 MiB of UTF-8 canonical JSON plus stored normalized JSON; duplicate receipts do not consume additional budget. Genuine new observations grow immutable history. Exhaustion fails closed with a redacted 503 and increments a saturating scalar rejection counter per source. No raw body is retained for reprocessing. Operators disconnect an exhausted source, preserve its immutable history/results, and register a new source/grant to begin a new explicitly incomplete history period. No destructive pruning or automatic cross-source history merge. Operation metadata conflicts are rejected before acknowledgement.

## Producer identity and evidence semantics

Argo's native `OperationState` has start/completion times and original requested operation, but no universal operation UUID. A Git SHA or start time alone must not be invented as universal rollout identity. First supported producer requires an explicit stable `clio.operation-id` UUID in the original operation's `info` entries, carried through `status.operationState.operation.info`. Deployment automation supplies a fresh UUID for each operation and preserves it across that operation's notifications. The sandbox uses explicitly identified manual operations. The first prerequisite probe used a direct Kubernetes patch and retained an empty initiatedBy; it does not prove Argo API RBAC. The production runbook must use an authorized Argo API/CLI sync with operation info and preserve initiatedBy as provenance; this producer path and its info support were verified against the pinned controller during implementation. Autonomous operations without this enrichment are unsupported and must be reported as an ingestion gap; never silently counted.

`operation_revision` is immutable for that operation (contract value `v1`); notification revision is a deterministic SHA-256 digest of the exact normalized status fields (phase, health, status timestamp, exposure and source reference), excluding receipt time. Application resource versions are not used: notification bookkeeping can change them and cause self-triggering loops. Opaque notification digests identify content; they are not ordering proof. `operation_revision:v1` is a constant immutable metadata revision key required by the existing adapter, not Argo Application resourceVersion. Native retryCount remains provenance on the same UUID; it never becomes a new rollout identity. Multiple updates retain their own status IDs. Repeated operations with the same SHA retain distinct UUIDs. Conflicting reused IDs fail closed.

Operation kind comes from explicit trusted `clio.operation-kind` operation info, one of rollout/self_heal/retry/unknown; missing kind remains unknown. Sync success is not permission to infer rollout kind. First native template emits `consumer_exposure:false` and `application_provenance:null`. Application commit provenance and consumer exposure require a separately trusted, documented producer enrichment; the GitOps configuration SHA never becomes the application commit.

Use a custom notification trigger, never a catalog trigger keyed only by revision. Its oncePer key includes explicit operation UUID, terminal phase, health status and health transition timestamp; unmarked operations use native startedAt only as a gap-delivery discriminator, never as deployment identity; notification bookkeeping resource versions are excluded. Sandbox must prove two same-SHA operations produce two deliveries and that retries do not create a loop. The first native template supports terminal operations (Succeeded/Failed/Error) with a nonempty `syncResult.revision` and explicit operation UUID. Running/Terminating states, absent sync results and autonomous unmarked operations are declared gaps; an enriched producer may support them later through a reviewed contract. The template must safely JSON-encode all values and include only the granted single-source configuration identity. Multi-source applications are outside this first mapping contract and fail closed. Environment and configuration-repository identity come from deliberate operator mapping, not guessed Application labels. Native operation event timestamps remain distinct from trusted receipt observation. Status time is the later of operation `finishedAt` and health `lastTransitionTime`, provided both timestamps exist, operation completion is not earlier than `startedAt`, and neither timestamp is later than trusted receipt time; this timestamps the first supported conjunction of terminal phase and recorded health. Missing health transition or completion timestamps make that native event unsupported. A health observation is never backdated to sync completion. Future timestamps produce a gap without clamping or backdating; synchronize controller/API/database clocks. Preserve UTC native second precision and database microsecond observation precision, accepting equal native timestamps without inferring an order. Health is Application `status.health` observed while this operation remains current, not an operation-health measurement. First supported native observations must arrive within 10 minutes after finishedAt, otherwise record a horizon gap; later app recovery is not assigned to this operation. Health unchanged from before operation start remains an observation with false exposure, not evidence of newly healthy resources. Native consumer exposure remains false regardless of this conjunction; enriched exposure/provenance payloads are outside the first wire contract.

Native source history IDs were considered and deferred: they are unavailable as a universal identifier across Running/Failed/Error, are bounded/truncated, do not retain operation info, and can arrive after terminal state. Do not mix history-ID and UUID identity on the same operation. Autonomous/self-heal operations without info remain recorded gaps.

An exposure policy is necessary but insufficient: qualification still requires explicit authenticated consumer exposure, production scope, rollout kind, Succeeded phase and Healthy evidence. Native sandbox evidence remains unknown even when Synced/Healthy. GitHub corroboration is not automatically merged; explicit rollout correlation remains future work.

## Snapshot jobs, results and browser workflow

Owner requests a result against current connection revision, UUID request ID and closed whole-day UTC period, maximum 90 days, end not after server time. Identical enqueue replay returns the same run; changed inputs conflict. One pending/running run per service. Members read latest 25 scoped runs and individual results.

A separate local `worker:argo` uses database-clock leased claims, bounded retries and current connection/grant fencing. Acquisition consists of already accepted scoped receipts, not outbound provider calls. Snapshot captures receipts observed at or before its database cutoff; later receipts cannot rewrite a saved result. Derive exact deploymentBindings from scoped receipts at cutoff under the owner application-to-service attestation. Normalize Argo opaque revisions with their own strict parser and merge logic; do not reuse GitHub's timestamp-revision parser. Preserve earliest observations, immutable operation metadata and prior exposure across out-of-order deliveries.

Atomic completion stores private reconciled evidence, pinned validated OEMS snapshot, calculated metrics, digest and safe terminal result. Use unchanged OEMS revision `5908bb12cdf24e7528088237dff9dca4c10ff45f` through the imported contract pin. Public result shows selected window/cutoff/connection revision/pin, retained receipt/evidence counts at cutoff across all dates (not window-limited or complete), recorded gaps and rejection counters with observation-period labels, provisional frequency count and incomplete coverage. Unsupported metrics stay null. Receiver success never means transport history or metric coverage is complete.

Web gets a separate Live Argo panel alongside GitHub/mock workflows: configure granted source, disconnect, choose dates, enqueue, inspect history/detail, show setup-needed/unconnected/error/stale states. No secret or arbitrary endpoint fields. Owner controls and identity/query/revision fencing follow the existing live GitHub workflow. No live overview metrics in this slice.

## Verified sandbox evidence

On 2026-10-10, the dedicated `clio-argocd` Kind cluster ran pinned Kubernetes 1.36.4 and Argo CD 3.5.4 with the public guestbook at configuration revision `f58c7ed8cfe28ad70701c5923fdbd0154388ea9f`. All seven Argo pods were Ready. A scoped Argo API account could get/sync only `default/clio-guestbook`; actual patch and foreign sync returned 403. Native safe JSON, custom trigger identity, first-request 503 followed by identical-body retry, two UUIDs at one SHA, terminal-only delivery, aged health suppression and settled bookkeeping without loops were verified against the controller. Missing-finish notifications remain gated by the pinned controller before trigger evaluation.

The integrated receiver then accepted two new identified operations and one unmarked gap through the native controller, returning actual Clio 202 acknowledgements and durable receipt IDs. Owner-saved sandbox connection revision 1, separate private ingestion grant and explicit Application/service mapping were used. A temporary scoped Docker Desktop tunnel kept the API loopback-only; it is evaluation infrastructure, not hosted ingress. PostgreSQL retained three receipts, four evidence records and two distinct deployments. The leased worker stored an immutable OEMS snapshot and the signed-in browser showed two unknown qualifications, one missing-identity gap, false coverage, provisional count zero and unavailable rates. The reporting window was the prior closed UTC day; retained counts explicitly span all dates at cutoff. Existing mock history and GitHub setup-needed state were smoke-tested. See [producer and receiver proof](../../../infra/argocd/README.md) for exact public identities and limitations. Credentials remained outside Git and chat.

## Credential rotation and producer delivery gates

Rotate with an explicit interruption: disconnect source, persist the gap boundary, stop API/worker, replace the private credential and producer Secret through the operator's managed workflow, restart both, owner re-saves, then reconnect. No overlapping credentials or zero-loss rotation is claimed. Notifications may exhaust provider retries during the gap. Revocation removes the grant/credential and requires process restart; it does not delete historical evidence.

The destination cluster identity is operator-assigned and scoped by stable Argo instance plus exact destination server/name; the shared `kubernetes.default.svc` string is not globally unique. Project, repoURL and destination changes on an unchanged Application UID constitute scope drift. Multi-source and source-hydrator apps fail closed with recorded gaps; configuration revisions stay opaque strings, not assumed application commits.

Before implementation is considered complete, verify native safe JSON templating, Argo API/CLI info propagation and initiatedBy, custom trigger oncePer, retry behaviour after 5xx and notified-state bookkeeping in the pinned sandbox. Template simulation or manual POST alone does not meet the producer gate.

## Limits and later work

No hosted ingress/deployment model, self-service Argo ownership proof, arbitrary Argo URL client, automated polling/backfill, complete notification-delivery proof, automatic operation enrichment, monorepo/multi-source provenance, automatic exposure attestation, incident/recovery/change collectors or automatic evidence pruning. Local sandbox is not production and remains separate from Clio's mock datasets.
